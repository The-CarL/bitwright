# M0 feasibility evidence — 2026-10-01

**Status: candidate implemented; desktop acceptance remains open.** No CPU,
assembler, boot monitor, or circuit-owned input FIFO is implemented yet. The
approved M0 gate requires actual desktop mouse/display evidence before CPU work.

## Reproduction environment

- macOS 26.3.1 (a), build 25D771280a.
- Python 3.12.12 and Temurin JDK 21.0.12.1+1.
- Official Logisim-evolution 5.0.0 standalone JAR; SHA-256
  `6b368e894742c04cc83aa9830f869bcab0190ede4df43ad6fecdb89b3a23a41c`.
- Commands: `python3 tools/bw.py test` and `python3 tools/bw.py package`, with
  `JAVA_HOME` and `LOGISIM_JAR` selecting those exact local tools. On Linux, run
  the test command under `xvfb-run -a`; vector execution initializes Swing.
- Test output is captured locally in `build/test-results/`. CI retains those
  logs as an artifact. This report deliberately distinguishes command-line
  simulator evidence from desktop interaction.

The Python runner has ten passing unit tests for its validation and failure
boundaries. The circuit vectors run against the real pinned simulator, not a
Python reimplementation. The stock pixel test uses a version-specific native
image inspection adapter; it is development tooling only.

The native renders are in `build/renders/`. They are artifact renders, not
desktop screenshots. Layout inspection found a stock-video reset wire crossing
an X input connection; that collision was fixed and the pixel-path test added to
prevent a similar fault from passing a reset-only test.

## Bridge behavior and boundary

The Java contract suite passes **367 checks** covering pixel commands, coordinate/color handling,
reset/clear, queue capacity/overflow, packet stability, acknowledgements,
cloning, and mouse press/drag/release callbacks for all three buttons. The host
queue contains at most 256 packets; overflow drops new packets and is sticky.
The planned machine-side 16-event FIFO is absent from M0.

The custom canvas never paints because a host event arrived. Native gates route
mouse coordinates to the pixel bus and permit plotting only for a valid packet
with the primary button held. The bridge applies that command on a falling
clock edge. Its source and tests ship in the candidate package.

Inspection of the complete native Poke tool path showed that its synthesized
first callback is followed by the original host event. The bridge ignores the
synthetic no-button callback; it does not invent a primary button. The later
desktop smoke check below confirms primary-button click packets; other gesture
and button-routing acceptance remains open.

Review found that an arriving first event could otherwise be consumed on the
same falling edge before VALID had been exposed. ACK now requires previously
exposed VALID; regression cases cover that arrival race, an appended release,
and reset priority. The resulting JAR SHA-256 is
`fdc5373d9ab45340ad294e8a8f7f0f0e386cc0c874d54cd8adb0a4be1496e08f`.

## Performance limits of this evidence

On this machine, individual foundation-vector processes took approximately
0.7–1.3 seconds including JVM startup; RAM signature runs took approximately
0.6–0.8 seconds including startup. These tiny tests are **not** measurements of
computer cycles/second, instructions/second, or input latency. The terminal test
uses a three-second deadline only to stop an intentionally interactive process.

The proposed input-to-visible-response target of 250 ms has not been measured.
No full-computer performance or animation-rate claim is supported yet.

## Later live desktop smoke check

Initial automation attempts discovered the running Logisim application but timed
out when attaching by name, bundle ID, or path. Later in the same session, desktop
attachment succeeded. With the user watching, the agent operated Logisim-evolution
5.0.0 on `Downloads/bitwright-m0/circuits/bitwright.circ` and observed the following
results in the live application. This supersedes the earlier lack of any desktop
interaction evidence; it does not establish the remaining acceptance items below.

| Check | Observed desktop result |
| --- | --- |
| Stock Keyboard to TTY | Typed `HELLO BITWRIGHT` through the stock Keyboard; the phrase appeared visibly in TTY. |
| Click packet retention | With Ack=0, a canvas click showed Valid=1, X=60, Y=60, Buttons=`001`, and host queue=2. A second click increased the queue to 4 while the front packet remained unchanged. Ack=1 drained the queue. |
| Paused, single-cycle acknowledgement | Used the visible clock toolbar to pause ticks. With Ack=1 and a queued press/release pair, one full-cycle toolbar step changed queue=2 to queue=1, exposing Buttons=`000` at X=60, Y=60 with Valid=1. The next full cycle drained the queue to 0. Keyboard shortcuts were unreliable for controlling the clock during this check. |
| Stock pixel command | X=64, Y=64, Color=`100`, and Plot=1 produced a visible red center pixel after one cycle. |
| Clear behavior | Clear high cleared stock RGB Video immediately. The custom canvas cleared on the next falling-edge cycle. |
| Click painting | With the clock resumed, Plot=1, Ack=1, and Color=`111`, twenty actual canvas clicks produced a visible dotted `B`. The host queue returned to 0 and overflow remained 0. |

After the canvas demonstration, the agent clicked the stock Keyboard again and
attempted `typeText` with `KEYBOARD + PIXELS OK`, then `READY`, then individual
`r`, `e`, `a`, `d`, `y` key presses and Return. TTY still displayed only the
original `HELLO BITWRIGHT`, and the Keyboard buffer appeared empty. The cause is
unresolved; this observation does not distinguish application behavior from
automation/input routing. Keyboard refocusing under automation remains unverified,
while the initial text-entry success is confirmed.

Attempted automated drags produced sparse dots and unexpected control toggling.
The cause was not established. These attempts do not demonstrate continuous drag
routing and must not be described as a passing drag test or attributed to the
bridge without further investigation.

The final visible state had ticks running, Plot=1, Ack=1, Color=`111`, Clear=0,
and Reset=0. The dotted `B` remained on the canvas with host queue=0 and overflow=0.

## Desktop acceptance still required

The smoke observations above are partial acceptance evidence. Keep M0 open and
record platform, simulator version, outcome, and evidence for the remaining checks:

1. Extract into a fresh folder, disconnect networking, and open the candidate in
   the pinned desktop application. Verify both libraries, reset, and smoke-test
   text and pixels without network access.
2. Verify keyboard refocusing after canvas use, continuous drag routing, release
   outside the canvas, focus loss while a button is held, and platform handling
   of secondary/middle buttons.
3. Exercise stock pixel corners and all colors through the desktop controls;
   automated native tests already cover these, while the live check used the
   center red pixel and clear.
4. Exercise queue overflow and reset recovery in the live application, including
   dropped-release behavior. The successful small-queue click tests do not cover
   this boundary.
5. Save a disposable copy, close/reopen it, and repeat the text/pixel smoke checks.
   Do not replace generator-owned source with the simulator's rewritten copy.
6. Measure responsiveness at a stated tick rate. Keep startup time separate from
   steady input-to-visible-response latency.
