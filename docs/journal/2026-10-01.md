# 2026-10-01 — Begin the feasibility bench

## Question

Can native inspectable circuits, reliable automated failure detection, and real
mouse/display interaction coexist in a small offline Logisim-evolution project?

## Decisions

The approved v1 target uses an 8-bit datapath and 16-bit addresses. Single-bit
flip-flops and bulk RAM/ROM are allowed; arithmetic, selection, registers,
counters, and instruction control are built from gates. Host adapters are separate
from CPU-visible device logic. A source-available Java canvas may retain pixels
and capture input. The first implementation gate is M0, not the CPU.

## Work initiated

The architecture, opcode contract, roadmap, source-ownership policy, and scoped
backlog are recorded alongside the M0 implementation. The simulator target is
Logisim-evolution 5.0.0; the bench deliberately has no CPU or assembler. Native
fixtures, bridge source, test tooling, and packaging are implemented as an M0
candidate; that does not close the desktop acceptance gate.

## Evidence and open questions

Use the [M0 evidence report](../evidence/m0-2026-10-01.md) for actual command output, measured behavior, and
acceptance status. The packaged simulator returned zero for an intentionally
incorrect vector, confirming why the wrapper must validate printed pass/fail
counts. Both fixture sources passed four gate vectors and fifteen stateful storage
rows. The bridge passed 367 contract checks; callback tests cover all button bits
and arrival immediately before acknowledgement.

These checks do not assert that the desktop integration gate has passed. Real
mouse focus/release behavior, desktop text/pixel output, and an offline desktop
smoke test remain pending. Native command-line round trips and relocated loader
checks must be reported separately from GUI acceptance. Desktop automation could
not attach to the application during this session, so no desktop-interaction or
input-latency result is claimed and CPU work has not started. The inspected native
renderer outputs are circuit artifacts, not desktop screenshots.

Reading only the host poker adapter initially suggested that its synthesized first
press loses the button ID. Inspection of the full Poke tool path found that the
original event follows it. The bridge must ignore the synthetic callback and
process the real event; callback tests now cover this path, while actual desktop
routing still needs evidence. This is why the caller and adapter both matter
when reasoning about host integration.

Review also caught a queue race: a first event arriving just before an ACK edge
could be consumed before the circuit had seen it. Acknowledgement now requires
previously exposed VALID, and regression tests cover the race and reset priority.

Commit/release reference: pending the implementation commit and reviewed evidence.
