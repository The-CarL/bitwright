## Writing and publication

Write an entry when an experiment or milestone produces evidence. Each entry
should include the question, design, experiment, failure, measured result,
commit/release reference, and next uncertainty. Use a screenshot or small native
circuit when it helps readers reproduce the observation.

Never write a successful experiment retroactively from a design expectation.
Keep failed approaches that explain a real tradeoff; distinguish tests run from
tests merely planned. Add the commit reference after the work is committed.

The future blog/Forge sequence follows the keyboard/text-terminal v1 scope amended
on 2026-10-01, publishing only after the relevant milestones are completed:

1. **Where the primitives stop:** storage policy, stock keyboard/TTY boundary, and M0 evidence.
2. **Gates with memory:** the verified logic workbench, flags, and readable hierarchy.
3. **The first instruction:** fetch, clocks, controller, and the first RAM result.
4. **Programs and calls:** assembler, reference tests, pointers, and stack conventions.
5. **A terminal becomes a computer:** boot, buffering, help, memory dump/edit, program run, arithmetic, and memory tests.
6. **A computer others can open:** release reproducibility, terminal responsiveness, limitations, and lessons.

The earlier mouse/canvas experiment remains historical journal material and may
support a later optional article. It is not a required v1 chapter or release gate.
Preserve its actual successes and unresolved findings with a dated scope
amendment; do not retroactively present it as necessary to the narrowed project.

Only publish the corresponding result once its acceptance evidence exists. Forge
can present the same verified demos, diagrams, circuit downloads, and journal.
